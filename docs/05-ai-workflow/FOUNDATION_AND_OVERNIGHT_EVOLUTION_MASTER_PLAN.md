# PART 4 — 技术路线与架构

## 4.1 当前技术基线

当前已记录的主要技术方向：

- Vue 3.5。
- 原生 Three.js r187。
- GSAP 3.15。
- Pinia。
- TypeScript。
- React 19.3 + R3F 作为对照研究方向。
- Babylon.js 作为专项对照方向。

这是现阶段技术基线，不是永远不能改变的限制。

不要无理由推翻已经验证的路线。

## 4.2 技术选型原则

候选技术必须从以下方面评估：

- 实际能力。
- 性能。
- 开发效率。
- 生态成熟度。
- 文档质量。
- 社区维护。
- 许可证。
- 学习成本。
- 长期维护成本。
- 与当前项目的兼容性。

不要仅凭 GitHub Stars 决定是否引入。

不要仅凭一个漂亮 Demo 决定是否更换引擎。

## 4.3 三维引擎比较

继续保留：

- Vue 3 + Three.js。
- React + R3F。
- Vue 3 + Babylon.js。

但必须逐渐采用更加真实的对照测试。

至少验证：

1. 相同 GLB 模型加载。
2. 相同贴图。
3. 相同场景规格。
4. 大型模型。
5. 独立 Mesh。
6. 模型拆解。
7. 多场景切换。
8. 资源释放。
9. Shader。
10. 粒子。
11. 后期处理。
12. 长时间运行。

不同引擎的 Draw Calls 等指标不能脱离实际场景直接比较。

## 4.4 架构分层

建议：

```text
EXPERIENCE
    ↓
DESIGN SYSTEM
    ↓
DOMAIN ENGINE
    ↓
3D RUNTIME
    ↓
DATA & ASSETS
    ↓
DEV INFRASTRUCTURE
```

普通 Web 应用和 3D Runtime 必须保持相对独立。

未来即使更换 3D 引擎，也不应该重写全部产品业务逻辑。

建立可扩展的 3D Runtime。

# PART 8 — AUTOMOTIVE ASSET PIPELINE

这是 AUTOVERSE 的核心基础设施之一。

## 8.1 模型优先级

优先：

1. 完整拆解模型。
2. 高质量完整车型。
3. 有独立机械组件的模型。
4. 外观模型。
5. 程序化或工程示意模型。

## 8.2 模型质量分级

S：完整真实拆解。

A：高质量整车且支持独立组件交互。

B：外观模型加部分机械组件。

C：普通外观模型。

必须有真实依据。

不能因为 Mesh 数量多就判断模型是完整拆解。

## 8.3 模型格式

优先：

- GLB。
- glTF。

研究：

- Draco。
- Meshopt。
- KTX2。
- LOD。
- Texture Compression。
- Instancing。

## 8.4 资产元数据

建议：

```ts
interface AutomotiveAsset {
  assetId: string;
  name: string;
  category: string;
  brand?: string;
  model?: string;
  year?: string;
  source: string;
  license: string;
  attribution?: string;
  modelQuality: "S" | "A" | "B" | "C";
  modelType: "REAL" | "RECONSTRUCTED" | "SIMULATED";
  format: "GLB" | "GLTF";
  fileSize?: number;
  meshCount?: number;
  materialCount?: number;
  textureCount?: number;
  hasAnimation?: boolean;
  hasIndependentParts?: boolean;
  parts?: AutomotivePart[];
  verifiedAt?: string;
}
```

可以根据实际架构调整。

## 8.5 模型检查工具

- Material。
- Texture。
- Animation。
- Bounding Box。
- 文件大小。

- 可能存在的异常。

尝试识别：

- 车身。
- 发动机。
- 车轮。
- 电池。
- 座椅。
- 变速箱。

# PART 17 — AUTONOMOUS EVOLUTION LOOP

每轮执行：

```text
1. 审查项目当前状态
        ↓
2. 发现问题与机会
        ↓
3. 研究新技术与解决方案
        ↓
4. 评估价值、风险和成本
        ↓
5. 制定实施计划
        ↓
6. 实际编码与实现
        ↓
7. 运行和测试
        ↓
8. UI/UX 审查
        ↓
9. 性能审查
        ↓
10. 修复问题
        ↓
11. 更新文档与状态
        ↓
12. Git Commit / Push
        ↓
13. 规划下一轮
        ↓
14. 继续执行
```

每一轮必须回答：

- 当前最明显的短板是什么？
- 哪项改进价值最高？
- 有没有值得引入的新技术？

- 有没有值得借鉴的开源项目？
- UI/UX 是否有明显问题？
- 3D 视觉是否足够有辨识度？
- 交互是否有实际意义？
- 性能是否存在瓶颈？
- 是否需要重构？
- 下一轮应该做什么？

然后直接开始。

# PART 20 — Git 与交付规范

每个有意义的阶段都形成独立提交。

建议提交类型：

- docs。
- feat。
- fix。
- refactor。
- perf。
- test。
- chore。

提交前：

1. 检查 diff。
2. 检查敏感信息。
3. 检查无关文件。
4. 检查构建产物。
5. 检查依赖变化。
6. 检查文档同步。

禁止：

- Force Push。
- 未检查就覆盖历史。
- 删除有价值实验。
- 提交 node_modules。
- 提交未经许可的大型模型。
- 提交 API Key 或密钥。

阶段完成：

Commit → Push → 记录 SHA → 更新 PROJECT_STATE。

Push 失败时：

- 保留本地提交。
- 记录失败原因。
- 继续其他工作。
- 不进行破坏性 Git 操作。

# PART 23 — 停止条件

只有以下情况之一出现，才结束本次任务：

1. 本次可用 Token 或执行资源耗尽。
2. 当前环境达到时间或运行限制。
3. 出现无法恢复的环境阻塞。
4. 关键权限需要用户处理，且没有其他独立任务可继续。
5. 当前所有高价值任务均已完成，继续工作只会产生低价值内容。

如果一个阶段受阻，不代表整个任务失败。

寻找替代方案，继续其他工作。
